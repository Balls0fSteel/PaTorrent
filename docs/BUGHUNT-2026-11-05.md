Timestamp: 2026-11-05_082716_1793863636. Tree: `a34dacc0` (1.1.68). A read-only review of all five crates by ten parallel reviewers, one per area; every finding below was re-read at the cited lines in this session, and two were reproduced by running the code. Legend: **run** = reproduced by execution; **traced** = confirmed by reading the code path end to end; **plausible** = the defect is in the code but the trigger was not constructed in full.

**Status:** the five high findings were fixed in 1.1.69 and the twelve medium ones in 1.1.70 (CHANGELOG 2026-11-05), each with a test except the GTK quit (14, read only); the 21 low findings 18-38 were closed in 1.1.71-1.1.74 (2026-11-05_102610_1793870770): twenty fixed, each with a test except 30 (GTK, compiled on the Xubuntu VM) and 34 (needs a missing ICMP driver); 35 ruled out by a probe (SChannel creates no context on a partial ClientHello). ## High (fixed in 1.1.69)

1. **Web UI: the fixed bypass names work as session cookies** (`crates/nox/src/webui/api.rs:299-331`, traced). `authenticate` looks the `SID` cookie up in `State::sessions`, and the same map holds the bypass pseudo-sessions under the literal keys `apikey`, `local` and `subnet` (inserted at 326-330). While an API-key, loopback-bypass or whitelisted-subnet client has been active within `session_timeout` (the WebSocket tick refreshes them, `server.rs` ~593), a request from any address with `Cookie: SID=local` is logged in. Side effect: `search::check_password` (`search.rs:213`) removes the caller's session on a wrong password, which for a bypass key evicts the shared pseudo-session. Tests only try a random forged SID (`nox/tests/webui.rs:491, :1727`). Fix: keep bypass state out of the cookie lookup, or reject cookie values that are not 32 hex characters.

2. **A web seed host with a non-ASCII label panics the engine thread** (`crates/core/src/engine/web_seed.rs:223`, run). `is_idna` slices `l[..2]` and `l[2..4]` by byte; a label such as `aéb` (bytes `61 C3 A9 62`) puts index 2 inside `é` and panics ("byte index 2 is not a char boundary"). The host reaches it intact: `parse_url_components` (`util/string.rs:253`) rejects only control bytes, and `connect_to_url_seed` (`web_seed.rs:480`) evaluates `is_idna` first with `allow_idna` off by default. There is no `catch_unwind` in `crates/core`, so one `url-list` entry (or `ws=` in a magnet, or resume data) stops the `lt-network` thread and the whole session. libtorrent's `is_idna` indexes characters.

3. **A borrowed file name can span a separator, and can be empty, so a file's path collapses to the torrent root** (`crates/core/src/metainfo/torrent_info.rs:1050-1059` `borrowable`; `sanitize.rs:35-37` drops `/`; `file_storage.rs:342-346` `name_of` maps invalid UTF-8 to `""`, run). `borrowable` keeps the raw bytes whenever the sanitized path merely ends with them. A v2 file-tree key (or v1 path element) of the form `<tail of the parent dir>/<240 bytes>` sanitizes to something whose full path ends with the raw bytes, so the raw bytes, with their `/` and possibly starting mid-codepoint, become the stored name. Reproduced: name `é`, key `A9 2F` + 240 × `_` gives `name=""` and `path="dl/é"`, the root directory itself; name `a`, key `a/` + 240 × `a` gives a name containing `/` and the path `dl/a/a/aaa…`. The second case is inherited from upstream (`torrent_info.cpp:580-584`); the empty name is port-specific. No traversal (always a suffix of a sanitized path). Fix: require the borrowed bytes to start at an element boundary and be valid UTF-8, or compare against the last sanitized element only.

4. **A barrier on one torrent waits behind every checking thread's current check, and the writes it parks trip the global disk back-pressure** (`crates/core/src/disk/mod.rs:762-769` `barrier` counts `fenced_threads()` = I/O threads + `MAX_CHECKS`; `:935-950` the router fans it to every `lt-check-N`; `:1050-1055` a running `check_files` never polls its queue; `:971-974` jobs of a blocked storage are parked before `queued_write_bytes` is decremented at `:988`; traced). Scenario: torrent T (large, `check_rate_mb` capped) is being checked; the user changes a file priority, moves or renames downloading torrent S. All I/O threads block S, its peers keep sending, every parked `Job::Write` stays counted; once the count passes `max(max_queued_disk_bytes, 4 MiB)` (`engine/mod.rs:1220-1222`), `do_read_capped` (`:1229-1246`) sets quota 0 for every peer of every torrent until T's check (and any check queued behind it on that thread) finishes. libtorrent's fence waits only for the storage's own jobs. The same wait applies to stop/remove (`Fence`) but only delays `Completion::Fenced`.

5. **The remote-session protocol bypasses the path policy** (`crates/nox/src/webui/remote.rs:164` → `crates/core/src/remote/mod.rs:181-191` `dispatch`, traced). Every command other than the three handled locally goes straight to the engine, including `AddTorrent` (its `save_path`) and `MoveStorage`. `path_policy.rs` states that every path a request supplies is checked, and `commands.rs` / `api.rs` / `prefs.rs` do check, but a logged-in `/pa/remote` client's add and move paths are never checked, so `--webui-save-root` is void for that transport. Fix: check `AddTorrent` and `MoveStorage` paths in `remote.rs` before forwarding.

## Medium (fixed in 1.1.70)

6. **Alerts popped while waiting for tracker lists are thrown away** (`crates/gtk/src/app.rs:1606-1607` and `crates/win32/src/app.rs:2722-2723`, traced). `properties::fetch_trackers` (`frontend/src/properties.rs:415-442`) appends every alert it pops during up to 2 s to `a.alerts`; the next `on_alerts` does `take(&mut a.alerts)` then `pop_alerts(&mut alerts)`, and `AlertQueue::pop_all` (`core/src/alert.rs:714`) begins with `out.clear()`. Opening Properties while a torrent finishes, is added, fails or is removed loses that alert: no balloon or log line, `queue_top` not applied, a removed torrent's row stays all session (`TorrentList::update` only inserts), a pending Standby/Hibernate never fires. **Fixed in 1.1.70:** both `on_alerts` call the shared `properties::take_alerts`, which pops behind the saved alerts instead of into them. Test `saved_alerts_survive_the_next_take` (frontend).

7. **Peers kept across a magnet's file check never learn our piece set** (`crates/core/src/engine/wire.rs:265`, `mod.rs:2655-2712` `on_checked`, traced). The bitfield is written once, in `on_handshake`, from `t.picker.have()`. For a magnet whose files already exist, peers connect during the metadata fetch with no picker (HAVE_NONE), `start_torrent` keeps them, `on_checked` fills `have` and only sets `interest_dirty`. Those peers never become interested and we upload nothing to them until they reconnect. libtorrent's `files_checked()` re-inits every connection. Same for any handshake that completes while `t.checking`. **Fixed in 1.1.70:** `write_bitfield` sends nothing before the files are checked (libtorrent `ready_for_connections`) and marks `sent_bitfield`; `on_checked` sends the piece set and allowed-fast set (`write_allowed_fast`, each piece once) to every active peer still without it. Test `a_peer_kept_across_a_magnets_check_gets_our_piece_set` (`tests/wire_rules.rs`).

8. **Spurious snub when a request queue is refilled after 20 s idle** (`crates/core/src/engine/mod.rs:3329`, traced). `last_piece` is written only in `PeerConn::new`, on Unchoke (`wire.rs:346`), in `snub` (`:699`) and on a received block (`:876`); `request_blocks` does not touch it when the queue goes empty → non-empty. A peer that delivered its last block at T1 and had nothing to pick until T1+25 s is snubbed on the next tick after being given 4 requests: 4 CANCELs, a 1-block window until that block lands, "snubbed" in the status. libtorrent times the request, not the last piece. **Fixed in 1.1.70:** `request_blocks` resets `last_piece` when it refills an empty queue (libtorrent `m_requested`). Test `a_request_after_an_idle_spell_is_not_snubbed_at_once` (about 25 s).

9. **Choking silently drops allowed-fast requests we accepted** (`crates/core/src/engine/mod.rs:3762-3782` `set_choke`, traced). `upload_queue` and `reads_in_flight` are drained, and the REJECT loop skips `fast_set` pieces, so requests that `on_request` (`wire.rs:721`) accepted under BEP 6 are neither served nor rejected. The peer waits its request timeout and snubs us. libtorrent keeps and serves `m_accept_fast` requests across a choke. **Fixed in 1.1.70:** `set_choke` retains the `fast_set` entries of `upload_queue` and `reads_in_flight` and rejects only the dropped ones. Test `a_choke_keeps_the_allowed_fast_requests_it_accepted`.

10. **UPnP: the lease refresh spins the engine loop after a mapping was deleted** (`crates/core/src/engine/upnp.rs:1108-1128` `on_expire`, `:1070-1104` `update_map`, `:1036-1054` the unmap reply, traced). `update_map` sets `expires = now + PENDING_EXPIRY` for Del too; the unmap reply sets `protocol = None` and leaves `expires`. When it passes, `on_expire` sets `Add`, `update_map` returns at the `protocol.is_none()` branch without touching `expires`, `refresh_at` lands in the past, `service()` (`:362-364`) runs `on_expire` again at once, and the engine's poll deadline (`engine/mod.rs:497`, `portmap.deadline()`) is zero: 100 % CPU plus one "does not need updating" log line per iteration until the slot is reused or the mapper closes. Trigger: a listen-port or network change (`portmap.rs:441` `remap_ports` → `delete_mapping`). libtorrent resets `expires` before calling `update_map`. **Fixed in 1.1.70:** `on_expire` clears `expires` before the refresh, as libtorrent does; the spin began at the lease refresh (lease × 3/4), not 30 s after the unmap. Test `a_deleted_mapping_does_not_spin_the_refresh`.

11. **UPnP: closing the mapper with an AddPortMapping in flight leaves `pending()` true forever** (`upnp.rs:926-928`, `:1164-1183` `close`, `:191-193` `pending`, reviewer trace). `close()` marks the in-flight mapping Del and `update_map` returns because `d.conn.is_some()`; when the Map reply arrives the `closing` early return skips `next()`, so the delete is never sent. The mapping stays on the router, shutdown (`engine/mod.rs:740`) waits the full `stop_tracker_timeout`, and a mapper closed by an interface change sits in `portmap.closing` for the session. **Fixed in 1.1.70:** the Map reply's closing branch hands the slot on (`next`), so the Del goes out; `pending()` ignores a disabled device, whose Del marks could never be sent. Test `closing_with_a_map_in_flight_still_deletes_the_mapping`.

12. **`--daemon` and the Windows service: four path options are never made absolute** (`crates/nox/src/main.rs:509-532` `absolutize` covers save, state, config dir, ip filter, pid file, log, move-on-complete and sources but not `webui_cert`, `webui_key`, `webui_save_roots`, `import_dir`; `daemon.rs:360` `chdir("/")` runs before `start_webui` and `import_torrents`; traced). `run --daemon --webui 8080 --webui-cert cert.pem` fails with "not found"; `--webui-save-root dl` keeps the relative root, `PathPolicy::check` never matches, and the Web UI refuses every save path. `service.rs:118-129` `PATH_OPTIONS` omits `--webui-save-root` and `--import-dir`, so an installed service starting in System32 refuses every path the same way. `daemon_paths_are_made_absolute` does not cover these. **Fixed in 1.1.70:** `absolutize` covers the four, `PATH_OPTIONS` has twelve entries; `daemon_paths_are_made_absolute` and `install_makes_paths_absolute_and_keeps_the_rest` check them.

13. **Win32 Search: the selection is re-applied to the wrong results after a source answers** (`crates/win32/src/search.rs:613-616`, `:795-803`, traced). `WM_APP_SEARCH` runs `Search::collect`, whose `merge` (`frontend/src/search/worker.rs:318-348`) re-sorts `results` by seeders; `refill` then builds `keep` from `st.rows` (indices into the pre-merge Vec) against the post-merge Vec, so the row that now sits at the old index is highlighted and Add/Enter fetches it. Fix: compute `keep` before `collect`, or keep selected keys. **Fixed in 1.1.70:** `WM_APP_SEARCH` reads the selected results' keys (`selected_keys`) before `collect` and refills with them (`refill_keeping`). Test `the_selection_follows_a_late_source`.

14. **GTK: a quit during the closing window hard-exits and abandons the engine's save** (`crates/gtk/src/app.rs:1472-1484` `quit_app`, `:1572` `shutdown` takes `APP`, `:329`, traced). The tray stays alive until `app.run()` returns, so the tray's Exit, SIGTERM or Ctrl+C after the main window closed finds `APP` empty, takes the "nothing started yet" branch and calls `gio::Application::quit()` while the closing window's session is still flushing resume data. **Fixed in 1.1.70:** `shutdown` sets a `CLOSING` flag before `closing::start`, and `quit_app` returns while it is set; the closing window ends the application. Read and clippy-checked, not run (no GTK build here); no test.

15. **`fetch.rs` frames the response with the lenient parser but builds it with the strict one** (`crates/core/src/net/fetch.rs:624-640`, `proto/http.rs:265`, traced). A header with Latin-1 bytes (`Content-Disposition: filename="M\xFCnchen.torrent"`) passes `http_parser::parse_head`, the body is received in full, then `from_utf8` fails and the .torrent download ends with "invalid HTTP header". A `100 Continue` before the real head makes the strict parser report "truncated"; a `103 Early Hints` becomes the framing and a `Status(103)` error. Lenient takes the last `Content-Length`, strict the first. **Fixed in 1.1.70:** the response is built from the lenient head (`head_response`, non-UTF-8 bytes read as Latin-1, a bare CR still refused) and the strict parser is seeded with it (`ResponseParser::start_body`) to decode the body only; the lenient parser skips every 1xx head. Tests `interim_heads_and_latin1_headers`, `every_interim_response_is_skipped`, `header_bytes_outside_utf8_read_as_latin1`.

16. **Folder watcher: a failed add drops every pending entry with the same name** (`crates/frontend/src/torrent_folders.rs:549-561`, traced). `AddTorrentFailed { name }` runs `retain` by name only. Two auto-loaded files whose info `name` matches (the second a duplicate) lose both pendings, so the first is never renamed `.loaded` or deleted and the poller will not hand it out again. Magnet pendings have an empty name, and a failed magnet (a duplicate, or a bad URI with no `dn`) raises `AddTorrentFailed { name: "" }` (`engine/mod.rs:1968-1976`), which wipes every pending magnet's "store the .torrent when metadata arrives" mark. Fix: key by info-hash. **Fixed in 1.1.70:** `AddTorrentFailed` carries `info_hashes: Option<InfoHashes>` (set for a duplicate, decoded resume data or a duplicate magnet; `None` when the source did not parse; remote protocol 15) and the watcher removes only that pending. Test `a_failed_add_drops_its_own_pending_only`.

17. **Win32: a second instance's torrents vanish when the first does not pump for 5 s** (`crates/win32/src/main.rs:171-193`, traced). `SendMessageTimeoutW(.., SMTO_ABORTIFHUNG, 5000)` returning 0 is reported only for `ERROR_ACCESS_DENIED` or an exiting window; a timeout still returns `true` ("another instance took the arguments") and the new process exits. The GUI thread does block that long in places (`add_sources` reads .torrent files from a share on the GUI thread, `app.rs:4260`; a large `on_alerts` batch). **Fixed in 1.1.70:** `instance::outcome` classifies the send (Taken, Refused, Unanswered); an unanswered send is repeated every 100 ms while the window is there (Windows retracts a message its receiver did not pick up), and the second instance takes over if it goes. Test `a_hand_over_that_timed_out_is_not_taken`.

## Inherited quirks, not reported as bugs

- A v2-only single-file torrent with an unaligned size parses as two files (file + tail pad), so `MULTIFILE` is set and a `url-list` web seed gets a trailing slash and requests `…/f/f` (`torrent_info.rs:447`, `file_storage.rs:330-345`). Upstream behaves the same.
- `local_service_announce_interval = 0` gives a 1 ms LSD announce period; `on_udp_readable`'s `Err(_) => continue` would spin on a persistent non-WouldBlock error. No trigger under default settings.
- `json.rs` `hex4` accepts `\u+041` (a leading `+`). Harmless.

## Ruled out after tracing

HTTP parsing limits and smuggling defences, WebSocket framing, the JSON parser, `path_policy` shapes (UNC, `C:foo`, `..`, streams, links), the login route and CSRF checks, the updater's hash-then-rename and re-check under lock, the archive extractor's `safe_path`, version comparison, sort comparators, placeholder filling, settings round-trips, importer indices, bencode token limits, piece and pad math, DHT message and routing-table bounds, tracker interval floors, PEX and LSD parsing, uTP wrap arithmetic and extension parsing, MSE padding and key derivation, SOCKS replies, TLS extra-buffer handling, `WM_COPYDATA` bounds, GDI object lifetimes, GTK `RefCell` re-entrancy and list positions, the pid-file and signal handling, the service control handler and shutdown order.
