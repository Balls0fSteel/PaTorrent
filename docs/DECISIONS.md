# Project decisions

Last updated: 2026-10-27_091619_1793088979

Active decisions D1-D35. D1-D26 were extracted from the [plan snapshot](archive/PLAN-2026-10-23.md); D27-D30 record the current artwork direction; D31-D33 the installer, the update check and the website; D34 the release path to 1.0; D35 the V1.1 scope. Read the relevant rows when a task needs their rationale; [PLAN.md](../PLAN.md) is the current work summary.

> Implementation note: D3 records the approved write-back-cache design. The current implementation writes directly to files and has a per-disk-thread read cache; see [ARCHITECTURE.md](ARCHITECTURE.md) and [BACKLOG.md](BACKLOG.md#disk-and-storage). This extraction does not amend that decision.

Approved 2026-10-15 (D1–D8 as proposed; D9–D13 resolve Q3–Q7 with the recommended options).

| # | Decision | Rationale |
|---|---|---|
| D1 | The engine is a Rust port of libtorrent 2.0.11 (tag `v2.0.11`, BSD-3). No FFI, nothing linked. | Monolithic, lean, fully ours; libtorrent's proven algorithms and tests. |
| D2 | One network thread on **mio**. Protocols written sans-IO. Disk thread pool. Resolver thread. | libtorrent's own scaling model. mio is the smallest portable event loop (IOCP / epoll / kqueue). |
| D3 | Disk I/O uses pread/pwrite plus our own write-back cache. No mmap. | Avoids libtorrent 2.0's mmap memory and network-drive problems. Scales. |
| D4 | Dependencies: engine = `std` + `mio` + OS TLS; Win32 GUI = `windows-sys` only; everything else ported or written in-house. | Lean and monolithic; full control over size and performance. |
| D5 | Persistence: one resume DB + one metadata pack (like µTorrent's `resume.dat`), not two files per torrent. Lazy-load info dicts. | Startup time and RAM at 10k+ torrents. |
| D6 | Targets: Windows 10+ x64 (Rust's tier-1 baseline), Linux x86_64/aarch64, FreeBSD/OpenBSD. | Rust dropped pre-Windows-10 support from its tier-1 targets in 1.78. |
| D7 | Windows: static CRT, single `.exe`, portable mode (settings beside the exe), like µTorrent. | No installer or runtime needed. |
| D8 | Port libtorrent's tests with each module. Fuzz every parser. Deterministic swarm simulator. | Correctness without libtorrent's simulator. |
| D9 (Q3) | TLS is OS-native: SChannel on Windows, system OpenSSL / LibreSSL on Unix, behind a thin trait; Secure Transport (Security.framework) on macOS, which has no linkable OpenSSL (2026-10-21_225032_1792615832). | Almost no added binary size; the OS patches TLS. Built in `core::net::tls` with no new crates: SChannel through more `windows-sys` features, OpenSSL through hand-written declarations of a dozen stable functions, so Unix builds link the system `libssl` / `libcrypto` (Linux needs `libssl-dev` to build; FreeBSD has it in base). |
| D10 (Q4) | nox exposes a qBittorrent WebAPI v2-compatible subset (incremental `sync/maindata`). Since D18 it is a compatibility shim beside the native API, translating from the same cache; it never shapes a native feature. | Works with Sonarr, Radarr, Prowlarr and mobile apps. |
| D11 (Q5) | The Linux/BSD GUI uses GTK 4 via gtk4-rs. | Maintained bindings. Memory can be trimmed with the Cairo renderer if needed. |
| D12 (Q6) | Windows 10+ x64 only, on stable Rust. ARM64 Windows comes later as an extra CI target. No Windows 7/8.1, no 32-bit. | No nightly/`build-std`; tier-1 target. |
| D13 (Q7) | Strict µTorrent 2.2.1 look by default: classic list view, 2.2.1 layout, menus and toolbar order. Allowed modern necessities: per-monitor DPI scaling and long paths. An optional dark mode may come later, never as the default. | Faithful clone first. |
| D14 (Q9) | Coverage-guided fuzzing with cargo-fuzz on nightly, in a separate `fuzz/` workspace. The internal parsers reach it through the `fuzzing` feature of `patorrent-core` (hidden module `fuzzing`). CI fuzzes each target on Linux: 2 min per push to main that touches the engine, 30 min weekly. | Nightly stays out of the product build (D12 still holds). Linux CI needs no ASan setup. |
| D15 (Q1) | License: **PolyForm Noncommercial 1.0.0**, copyright **DukeCorp1996** (`LICENSE.md` with a `Required Notice:` line, SPDX `PolyForm-Noncommercial-1.0.0` in every manifest). Ported libtorrent code also keeps its BSD-3 notice. `LICENSE.md` ships in `dist\` and the CI artifact, `patorrent-nox --license` prints it, and the About box names it. | The owner wants no commercial use and their own name as author. Accepted consequence: source-available, not OSI open source, so no Debian/Fedora/F-Droid packaging. |
| D16 (Q2, Q8) | Name: **PaTorrent** (long name **PatinaTorrent**; a patina is the good kind of rust). Peer-ID prefix `-PA0100-`, User-Agent `PaTorrent/<version>`, BEP 10 `v` = `PaTorrent <version>`. Crates `patorrent-core` / `-frontend` / `-nox`, binary `patorrent.exe`, `%APPDATA%\PaTorrent`, `patorrent.ini`. `LR` stays mapped to the Android LibreTorrent in our peer table. | "LibreTorrent" was taken (Android, peer ID `LR`) and "libre" is wrong under D15. The owner turned down Ferrite (`Fe` reads badly) and Oxbit. `PA` is free in libtorrent's table and the BEP 20 list. |
| D17 (Q8) | No peer-ID spoofing. PaTorrent always reports itself. | A borrowed ID with this engine's fingerprint gets accounts banned on private trackers and misreports the client. |
| D18 | The Web UI is our own, not qBittorrent's: the µTorrent 2.2.1 main window in a browser, driven by a native push API (`/pa/ws` WebSocket down, JSON `POST`s up) designed from what the page needs. The page is a thin terminal of `patorrent-frontend`: the server runs the filtered, sorted `TorrentList` per client and sends formatted cells for the visible window only. No framework, no build step, embedded. The qBittorrent subset (D10) stays as a shim. Design: [docs/WEBUI.md](WEBUI.md). | Parity with the desktop for free (one `frontend` decides what is shown), 10,000 torrents without the page holding them, works on a phone, keeps the Sonarr / Radarr ecosystem at no design cost. Decided with the owner 2026-10-17. |
| D19 | **1.0 scope** (owner, 2026-10-19_230101_1792443661): the Win32 GUI, the GTK GUI (Phase 7) and nox; BitTorrent v2 and hybrid torrents (Phase 8, BEP 52: adding, downloading, seeding, creating; BEP 44 / 51 / 55 stay after 1.0 unless they come cheap); localisation; the Web UI over HTTPS and the GUIs' remote mode (Phase 6). | The owner wants a complete client at 1.0, not a Windows-only preview. |
| D20 | **Translations**: every user-visible string goes through string tables (one per language, shared by the three frontends), translated in full by Claude from the English table; English is the source and the fallback. | No translator community yet; whole-table machine translation is good enough to start and is redone when strings change. |
| D21 | **Scale before size** (2026-10-19_230101_1792443661): the 1.0 gate is 100,000 torrents loaded on a low-end PC ("µTorrent on a potato"), with idle CPU and responsiveness the measure. The empty-session working set of about 20 MB is accepted; memory is optimised later, and only where a measurement shows it is worth it (the 12 MB target is dropped). | The point of the project is lean and very powerful at scale, not a few MB at zero torrents. |
| D22 | **Distribution** (2026-10-19_230101_1792443661): Windows as the portable `.exe` (D7, a zip with LICENSE.md and the notices); Linux as AppImage and Flatpak, plus plain binary tarballs; no distro packages (D15 is not free software, and distro packages lag). macOS release built in CI without a Mac (GitHub-hosted macOS runners, as qBittorrent does), see D23 and D25. | Self-contained packages we control and update on our own schedule. |
| D23 (Q12) | **macOS GUI** (owner, 2026-10-19_230332_1792443812): the Phase 7 GTK 4 GUI, built for macOS too, in an `.app` bundling GTK and its libraries (x86_64 and arm64, ad-hoc signed). Mac-specific pieces: the menu bar through `GtkApplication`'s menubar (macOS shows it as the global menu), an `NSStatusItem` tray in place of StatusNotifierItem, `.torrent` / `magnet:` registration through the bundle's `Info.plist`, Login Items for autostart. | One GUI for Linux, BSD and macOS; GTK 4 looks good on macOS and the frontend model is shared already. |
| D24 (Q13) | **Languages** (owner, 2026-10-19_230536_1792443936): a broad first set, about the size of µTorrent 2.2.1's: Arabic, Bulgarian, Catalan, Chinese (Simplified and Traditional), Croatian, Czech, Danish, Dutch, Finnish, French, German, Greek, Hebrew, Hungarian, Indonesian, Italian, Japanese, Korean, Norwegian Bokmål, Persian, Polish, Portuguese (Brazil and Portugal), Romanian, Russian, Serbian, Slovak, Spanish, Swedish, Thai, Turkish, Ukrainian, Vietnamese. Translated from our English table (D20). µTorrent's own `.lng` files are not copied or vendored: they belong to BitTorrent Inc. and their translators, and D15 needs text we can license (as with qBittorrent's GPL Web UI). Arabic, Hebrew and Persian need right-to-left layouts (`WS_EX_LAYOUTRTL` on Win32, GTK's text direction, `dir="rtl"` in the page). | Wide reach from the start; the cost of a language is a table, not a translator. |
| D25 (Q14) | **Public repository** (owner, 2026-10-19_230536_1792443936), still under PolyForm Noncommercial (D15), with a pre-alpha "not ready for use" warning at the top of the README until a release says otherwise. | Free CI (macOS runners included), Flathub builds from the public source, and early feedback. |
| D26 (Q15) | **How the translations ship** (owner, 2026-10-20_212035_1792524035): the translated tables are compiled into every binary (the Win32 GUI, the GTK GUI, nox), deflated, and inflated at start with `util::puff`, the chosen language's table only. `PATORRENT_LANG=<file>.lng` still loads a loose table for translators. | One file stays one file (D7); deflated, the 33 tables (about 0.9 MB as text) add about a quarter of that; no missing or stale `.lng` beside the executable; the inflater is in the tree already. |
| D27 | **UI artwork** (owner go-ahead, 2026-10-26_100209_1793005329): regenerate all 131 symbols as one bold family with native pixel-fitted small drawings, separate large variants, light/dark and monochrome proofs; no active tile family. Colour encodes operational activity: paused amber and stopped grey regardless of completion, with checks for completeness. Force uses lightning; stalled uses !. Use the current Verdigris identity for About. The eight intentional reuse pairs are listed in the artwork manifest/README. | Systemic small-size and silhouette failures affect more than the 47 flagged icons. Deliver the artwork first, then integrate the 24 shared runtime symbols and 11 toolbar actions and validate platforms. Final app-brand choice remains provisional. |
| D28 | **Network and tracker icon bases** (owner, 2026-10-26_101801_1793006281): network-ok, network-no-incoming and offline share an arrow entering a port/ring, with check, ! and × badges. The Trackers tab and all four tracker states share a radio tower (no top dot), with check, refresh, × and … badges; reannounce = tracker-updating. completed/tracker-working leaves the reuse allowlist. | The revision 3 plug read as a fork and the tracker states had no common base; one base per family makes the shipped status-bar and Trackers-tab icons read as sets. |
| D29 | **Revision 5 icon bases** (owner, 2026-10-26_115602_1793012162; amends D28, accepting the [revision 4 review](../assets/ui-icon-explorations/review-2026-10-26/revision4/REPORT.md)'s recommendations): network = a closed port ring with the arrowhead inside it; if that still fails at 16 px, a globe with the status badge (no arrow). Tracker states and reannounce = the full Trackers-tab tower, narrowed, with 5 × 5 badges. Add URL = a single chain link with the plus badge, replacing the magnet. | In revision 4 the open ring plus a corner badge read as "→?", the compact tower as a figure and the tilted magnet as a letter. |
| D30 | **Revision 6 icon bases** (owner, 2026-10-26_143434_1793021674; amends D29 after the [revision 5 review](../assets/ui-icon-explorations/review-2026-10-26/revision5/REPORT.md)): the tracker states and reannounce use a pylon in x 1-8 with the broadcast arcs above its apex and splayed legs (option a); the Trackers tab is redrawn to match. Network uses D29's globe fallback with the same check, ! and × badges, no arrow. | The closed port read as an eye or key; two side arcs beside a 5 × 5 badge left room only for 4 px straight legs, which read as the letter "A". |
| D31 | **Windows installer** (owner, 2026-10-27_083359_1793086439; amends D7 and D22): Windows ships an NSIS installer, `patorrent-<version>-windows-x64-setup.exe` (`packaging/windows/`), beside the unchanged portable zip. It installs for the current user into `%LOCALAPPDATA%\Programs\PaTorrent` without elevation by default, as µTorrent installed per user, or for all users into Program Files by starting itself again through UAC; settings stay in `%APPDATA%\PaTorrent` (no `patorrent.ini` beside the exe). Associations are written only by `patorrent.exe --associate` (one implementation, HKCU); the uninstaller runs `--unregister` and keeps the settings unless asked. Upgrades install over the same folder. | Users expect a Start menu entry, an uninstaller and an in-place upgrade from the update notice (D32). NSIS because it is installed here and in the release job (pinned, checksum-checked), with no third-party plugins; MultiUser.nsh elevates at start, so the setup relaunches itself instead. |
| D32 | **Update check** (owner, 2026-10-27_083359_1793086439): the GUIs only tell; they never download or install. They read the website's `update.txt` (`stable=`, `prerelease=`, written from the GitHub releases, D33) 10 s after the start and every 12 h; a newer version shows for one minute at the start of the status bar and in the Logger, and a click opens its release page. Help > Check for Updates answers in a message box. Preferences > General > Privacy: "Check for updates automatically" (on) and "Update to beta versions" (off), as in µTorrent; a pre-release build is offered pre-releases anyway. Off in a Flatpak and in builds with `PATORRENT_NO_UPDATE_CHECK`; nox has none yet. | The owner cannot host downloads and wanted no pop-up. A static file on GitHub Pages has no API rate limit, is served from a CDN, changes only when the owner publishes a release, and can carry more keys later. |
| D33 | **Website** (owner, 2026-10-27_083359_1793086439): <https://balls0fsteel.github.io/PaTorrent/>, hand-written static pages in `site/` (no framework, no external fonts, scripts or analytics), built by `site/build.py` from the releases API and deployed by `.github/workflows/pages.yml` on site changes, release events, weekly and by hand ([WEBSITE.md](WEBSITE.md)). It hosts the download guide, FAQ, documentation links and `update.txt`; the multilingual wiki (V2.0 goal 4) comes later. | Free hosting tied to the releases, nothing to maintain beyond the repository, and nothing that tracks visitors. |
| D34 | **1.0 without a second candidate** (owner, 2026-10-27_091619_1793088979; amends the release path of D19, not its scope): rc.1 runs fine, so the next release is 1.0.0. (Its tagged build failed on the Flatpak metainfo, so the first stable release is 1.0.1; owner, 2026-10-27_104216_1793094136.) The Road to 1.0 hand checks still open (items 2-13) no longer block it; they continue as 1.0.x validation, and what they find goes into 1.0.x patch releases. Item 14 (version, notes, draft inspection) still applies. | The whole D19 scope is implemented and rc.1 showed no problem to the owner; what remains is validation on machines and by testers the project does not have, which a stable release reaches sooner than another candidate. |
| D35 | **V1.1 scope** (owner, 2026-10-27_112013_1793096413): the toolbar's search box (where 2.2.1 had its web search) filters the torrent list by name, case-insensitively, on top of the category or label; Ctrl+F reaches it. File > Import reads qBittorrent's `BT_backup` and µTorrent's `resume.dat` (only reading them, and refused while that client runs) into libtorrent resume records, trusting their pieces where the files exist; nox has `run --import`. Compiled-in plugin hooks move to V2.0. | The name match is what users look for and stays cheap at 100,000 rows; the importers bring over existing users without a recheck and need no engine API beyond `TorrentSource::Resume`; hooks had no concrete first user to shape an API. |
