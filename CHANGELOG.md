## 2026-11-03_131614_1793708174: Version 1.1.49: portable mode everywhere, relative paths (D42 slice 6)

- **Portable on Linux/BSD:** `patorrent.ini` beside the binary (or beside the `.AppImage`; never in a Flatpak) makes its folder the root there too: the GTK client keeps settings and library in it (a profile in `profiles/<name>`), nox its `nox` folder (the flags and systemd still win). A portable folder that cannot be written is an error (`PortableReadOnly` in the GUIs, 34 machine translations; nox's `error:`), never a fall-back to the user's folders. macOS stays without portable mode (slice 7).
- **Relative paths:** in portable mode the paths inside the folder are written relative to it (`./Downloads`, `/` separators) and resolved at load: torrents' save paths and absolute renamed files in `resume.db` (`SessionParams.portable_root` -> `Store::open_in`), Preferences' folders, the IP filter file, the Add dialog's recent folders and awaiting magnets' folders (`Prefs`, `profile::is_path_key`), the RSS filters' save folders (`rss.dat`). In memory every path stays absolute; paths outside the folder stay absolute; existing absolute ones inside it become relative at their next save. New `patorrent_core::util::portable`.
- **First start of a portable folder:** downloads go to its `Downloads` (and a random port, 1.1.45). The update offer treats a portable copy inside an install folder as portable (the release page, not the setup).
- **Downgrade note:** a portable folder written by this version needs it or later: 1.1.48 and earlier would read `./Downloads` against their working directory.
- **Checked:** unit tests (the path rules, UNC and other drives, `..` refused, the store, `Prefs`, `rss.dat`, the candidate folder), a nox integration test (a copied binary with `patorrent.ini`: state in `nox`, `resume` holds `./Downloads`, the folder renamed and started from elsewhere finds its data and seeds), 1,549 workspace tests, clippy for four targets; a fresh portable `patorrent.exe` wrote `dir.download=./Downloads`. Left out: the Web UI's categories (`webui.json`). Not run: Linux portable (tarball, AppImage), the Samba move.

## 2026-11-03_124252_1793706172: Version 1.1.46: associations and autostart per profile (D42 slice 3)

- **Windows:** a profile's open command is `"<exe>" --profile <name> --shell "%1"` (the profile before `--shell`, SEC-18) and its autostart a `Run` value of its own (`PaTorrent (work)`). A box is checked only in the profile the command names, so one profile at a time owns `.torrent` and `magnet:`; ticking it in another takes it over, and the General page then names the owner (`AssocOtherProfile`, 34 machine translations). `upgrade` rewrites only its own profile's commands; the installer's `--associate` writes the default profile; `--unregister` removes every profile's associations and `Run` values for this exe.
- **Linux/BSD:** a named profile writes `<APP_ID>.profile_<name>.desktop` at its start (its application id, so Wayland finds the window's icon; `Name=PaTorrent (work)`, `NoDisplay=true`, `Icon=<APP_ID>`), in the host's `~/.local/share/applications` inside the Flatpak (`flatpak run --command=patorrent-gtk <APP_ID> --profile <name>`). The MIME defaults and the autostart entry name it; `integration::starts` compares the profile. In the Flatpak only the default profile can autostart (one portal grant per application); the page says so when asked.
- **macOS:** a LaunchAgent per profile (`<APP_ID>.<name>.plist`, label likewise); a named profile cannot take the associations (Launch Services opens the bundle), its boxes are greyed.
- **Checked:** new tests on a scratch registry tree (take-over, per-profile `Run`, upgrade, unregister of every profile) and for the profile's desktop entry; 1,538 workspace tests; clippy for four targets. Not checked on a desktop: GNOME/KDE dock icons, the Flatpak's host entry, the real registry.

## 2026-11-03_123456_1793705696: Version 1.1.45: ports for profiles (D42 slice 2)

- **UPnP:** `SessionParams.label` (`PaTorrent (work)`) is the routers' mapping description for a named profile; the default profile keeps the user agent. `Protocol` is exported from core; every `SessionParams` literal gained `..Default::default()`.
- **Web UI:** the Win32 page proposes the first free port from 8080 up while the Web UI is off and the stored port is the default; a bind failure says "port N is in use, perhaps by another PaTorrent profile" (`WebUiPortInUse`), nox prints the same.
